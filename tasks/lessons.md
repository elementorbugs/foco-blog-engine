# Lessons learned

Pruned quarterly. Keep under 60 lines.

## SEO / URL structure

- **A directory holds only what its name promises (2026-10-08).** I padded the "ADHD app directory" Parenting tab with printable planners (household, meal, cleaning) plus coaches, free web tools and a general guide, so no tab looked thin. Adi: "is that an app? you're making a mess." Every card must pass "is this post about apps?"; a thin tab is fine, filler is not. Same for any category, tag or hub list.

- **Un-merging a page means checking its canonical (2026-10-23).** #1047 got canonical -> /best-adhd-app/ for a planned merge (10-08), then was rewritten as a standalone page (10-20) with the canonical left in place, so Google kept treating it as the hub's duplicate and the cannibalization "fix" was dead on arrival. Any rewrite/retarget of an existing page: `curl` its live `<link rel="canonical">` and robots meta first, and again after pushing.

- **Keyword-in-slug beats short-slug for unbranded sites.** For hub pages targeting search keywords, put the keyword in the URL: `/adhd-resources/` not `/resources/`, `/adhd-tools/` not `/tools/`, `/adhd-glossary/` not `/glossary/`. Branded/utility pages (about, contact, pricing, founders) keep short slugs because nobody searches "tryfoco about". Mistake made: suggested `/resources/` for a hub page targeting "adhd resources" — user corrected to `/adhd-resources/`.

- **Feature sub-pages need the keyword too.** `/features/adhd-task-breakdown/` not `/features/task-breakdown/`. The `/features/` parent gives context but the sub-page's own keyword has to be in its slug.

- **RankMath title appends " - SiteName" automatically.** Don't put the brand name in the H1/title field yourself — it doubles. Page title should be just the topic; RankMath adds the suffix.

## Content selection / cloud sync

- **The daily automation runs from GitHub, NOT your local repo.** `.github/workflows/daily.yml` runs `0 15 * * *` (18:00 Israel), does a fresh `actions/checkout` of `github.com/elementorbugs/foco-blog-engine`, and runs `node daily-generate.js --count=3 --pull-gsc`. So ANY local change to engine code or data (priority-queue.json, daily-generate.js, blocked-keywords.json, create-post.js) has ZERO effect on the daily run until it is **committed AND pushed**. This caused the "off-list keywords" bug: the 15-keyword `priority-queue.json` and the queue-respecting logic lived only locally (`??` untracked + ` M` uncommitted), so the cloud kept running the old master-plan picker and produced off-list posts (adhd-signs-in-3-year-olds, adhd-sex, adhd-job). **A local `--dry-run` proves local behavior, NOT cloud behavior — they can diverge.** When the user reports the automation misbehaving: FIRST run `git status` and diff local vs `origin/main`; the fix is usually `git push`, not a code change. Fixed + pushed 2026-06-06 (commits fd1ce80, b28625f).
- The picker logic itself is correct: queue items get score 1e9, sort first, run 3/day in order, and drop out via the live-slug filter (`status=publish,future,draft`) as they publish. Latent risk: that fetch is `per_page=100` single-page; total live posts hit 98 on 2026-06-06, so once it passes 100 the filter will start missing slugs and may re-create dupes. Add pagination before then.

## JS string pitfalls

- **`String.replace(re, replacement)` treats `$1`, `$2`… in the REPLACEMENT string as backreferences** — even when they're really literal text like a price "$17/mo" or "$1.99". This silently corrupted post 2136: a chart label `$17/mo` became `<the matched H2>7/mo` (the `$1` pulled in capture group 1) and dumped the heading inside the chart. **Always pass a replacement FUNCTION** (`.replace(re, () => insertHtml)`) whenever the inserted text can contain `$` (prices, regex-y content, user text). Functions' return values are NOT subject to `$` substitution. Verify rendered output, not just that the PATCH returned 200.

## WordPress publishing

- **Redirects cannot be created over REST (2026-10-08).** `POST /rankmath/v1/updateRedirection` answers "New redirection created." but saves nothing; drafting the source post then gave a plain 404. Verify with `GET /wp-json/wp-abilities/v1/abilities/rank-math/get-redirections/run` (read-only, lists every redirect). To merge a post: create the 301 by hand in Rank Math → Redirections, confirm the 301 with curl, and only then draft the old post.

- **The Rank Math sitemap was frozen at 2026-09-22 for a month (found 2026-10-19).** post-sitemap.xml listed 90 of 101 posts, so nothing published after Sep 18 was in it, and saving the sitemap settings did not invalidate it. Fixed with Code Snippet #14 (`rank_math/sitemap/enable_caching` → false). After publishing, check that the new slug is in post-sitemap.xml; the get-sitemap-status ability's `estimated_count` vs the served `<loc>` count catches drift.

- **WP templates output H1 via `the_title()`. Body content must NOT have its own H1.** `single.php` line 13 and `page.php` line 14 both output `<h1><?php the_title(); ?></h1>`. If body content also starts with `<h1>`, the rendered page has duplicate H1s — Google flags as SEO error. **Always strip `<h1>` from body content before pushing.** `create-post.js` STEP 10.5 handles this automatically. For one-off page pushes via REST, strip H1 before sending the `content` field.

- **Pages don't get auto-injected FAQPage schema.** `create-post.js` only runs on Posts. For Pages with FAQ sections, manually add FAQPage schema via RankMath → Schema → Add FAQPage.

- **Local theme repo can drift from live theme on Cloudways.** When the user pastes their live header.php or footer.php, sync the local file before editing. The disk version may be stale.

- **Theme h2 is sized for landing-page hero (clamp 30-60px). Content Pages + blog post bodies need smaller H2.** Scope override with `body.page:not(.foco-page)` (Pages) and `.foco-app .blog-single article h2/h3` (post bodies). Without this, H2 visually dominates H1 on every content page.

## Light articles (dark theme + light reading area)

- **The light-article CSS is element-level + `!important`, so every dark component must opt back out — and anything OUTSIDE `<article>` never got covered at all.** Two failure modes, both found on `/body-doubling-adhd/` (26 pairs under 4.5:1):
  (a) *dark islands*: `.blog-single article strong{color:#160F22!important}` painted near-black text onto the near-black chart cards and the `.foco-bd-tool` widget — its H2 title, its intro `<p>`, and the `<strong>` step labels in every `progressTimeline` chart were invisible. 27 of 74 posts had it.
  (b) *chrome outside `<article>`*: the theme sets `.blog-single` white, and the light CSS only recoloured `article`, so the **comment form ("Leave a Reply", every field label) and the prev/next nav were white-on-white on all 74 posts**.
  Fixes live in the DARK ISLANDS + CHROME OUTSIDE `<article>` blocks of `light-articles.css`. **A new dark component just needs `class="foco-dark"`** — never hand-patch one widget (that is how the old standalone `/*foco-chart-fix*/` block appeared, and it only covered `p`/`li`/`figcaption`).
- **The theme's `.foco-app .blog-single article > *{color:var(--muted)}` (0,3,1) outranks any component class**, so a dark card's own `color:#fff` loses and its buttons inherit grey. Dark islands must set the container colour, not only the text elements.
- **Eyeballing a screenshot is not verification.** `node scripts/audit-contrast.js <url|file.html>` walks the rendered page, resolves the real background (gradients included) and lists every pair under 4.5:1. Run it on a local file BEFORE pushing, on the URL after. Occasional false positives if the external stylesheet loses the load race — re-run once to confirm.
- **Interactive widgets built for the dark theme go invisible on light posts, and nobody notices because they still "work".** The 6 timer posts shipped white digits + `background:rgba(255,255,255,.035)` cards: on `#FAF8FD` the readout was unreadable and the theme's `.foco-app button{background:0 0;color:inherit}` (0,1,1) out-specified the single-class button rule, so Start/Pause/Reset rendered as grey text. Rebuilt as a self-contained dark island (`timer-widget.js` + `apply-timer-design.js`, 2026-07-25). **Any new in-post widget: give it `foco-dark`, scope its CSS `.wrap .child` (0,2,0+) with `!important` on colour, and screenshot it on `#FAF8FD` before pushing.**
- **A post's injected light block can be stale even when `light-articles.css` is current.** All 6 timer posts still carried the v2 block, so the comment form and prev/next nav were white-on-white there long after the site-wide fix. `inject-light.mjs` only rewrites the posts you name, and it **skips drafts** (the 20-min post stayed stale). After editing a post's content, re-run inject-light for that slug and re-audit.

- **create-post.js ships posts with ZERO photos here (no .pexels-key in the root), and the dry run does not warn (2026-10-20).** Adi: "this post has no images at all" on /adhd-dopamine-menu/. After publishing, add 4-5 landscape Pexels photos (one per main H2) with a direct REST patch: key from C:/Users/USER/remindher-blog/.pexels-key, see add-dopamine-menu-photos.js. Use the API's src URL: old photos are not named pexels-photo-<id>.jpeg (6360 404ed). Check naturalWidth on the live page.

- **Printable posts: never embed whole letter-size planner pages (2026-10-20).** /household-planning-for-adhd/ showed full 8.5x11 PNGs (mostly white space, mascot on 2 of them), credit-line stock photos, no featured image, ~1,000 thin words; Adi: "a shameful post, horrible images". Show printables as cropped, mascot-free previews (render the printable HTML with `.mascot{display:none}` + `.page{height:auto}`, see fix-household-planning.js), pair them with relevant Pexels photos with no credit in the caption, and check `featured_media` is not 0.

- **The visual model for every post is /best-ai-calendar-apps-for-adhd/ (Adi, 2026-10-20).** Short answer + "Pick X if" bullets, an at-a-glance `foco-cmp2` table, then one designed showcase card per item followed by 2-3 paragraphs and a "Good to know". Stock photos as decoration and text tables of example data read as weak. For printables: `scripts/printable-showcase-figure.js` (pages fanned on a tinted card) and `scripts/day-schedule-figure.js` (example days as color-block cards); rebuilt /adhd-visual-schedule/ this way (rebuild-visual-schedule.js).

- **A button that links OFF-site gets the theme's purple link colour forced onto its text (2026-10-20).** The red Save-on-Pinterest button on #5078 rendered purple-on-red, while the PDF button (tryfoco.com href) stayed white. Inline style on any external-link button needs `color:#fff !important;background:... !important`. Check getComputedStyle(color) on the live page, not the source.

- **App images in posts are landscape, never portrait phone shots (Adi, 2026-10-20, twice).** I put a portrait FOCO screenshot on /best-apps-for-adults-with-adhd/ and left 5 on /best-adhd-planner/. List the media library first (width > height) and use the landscape app images there; FOCO ones must be mascot-free (foco-what-gets-you-moving.png, foco-decomposition-vs-initiation.png). 33 older posts still carry portrait pairs.

- **Product pages get the homepage design, not blog styling (Adi, 2026-10-20: /features/ "ugly, not our site's level").** It was a text article with emoji cards and the mascot. Rebuilt with `features-page/build.js` (reuses homepage-preview CSS + real app screenshots/videos). Any page with its own `.fh` design must be added to `EXCLUDE` in `scripts/build-light-pages-snippet.js` (snippet #12), or the light-page rules repaint its dark sections dark-on-dark.

- **Our YouTube video goes right after the answer box, not at the bottom (Adi, 2026-10-22: "why is the video at the bottom? some people like to watch").** `add-youtube-to-post.js` used to put it after Key Takeaways; it now inserts after `.foco-tldr`. Moved it up on the 5 vs posts that had one. A new card in `app-directory.json` is appended last in its tab, so move a new comparison to the top of its category and write a real `desc` (the auto one is a cut-off "Short answer: In the...").

- **New FOCO promo videos start from the ViralVSL cut (`src/demo/ClipDemo.tsx`, `vsl: true`), never from scratch (Adi, 2026-10-22: "terrible, not creative").** Memory `feedback_vsl_video_format` already said so; I built two silent text-over-footage reels instead and both were rejected. Narration + word-by-word Montserrat captions + app over blurred footage with chips/taps/confetti is the approved recipe; new footage only swaps in as b-roll.
- **A promo video needs one person and one story, not a montage (Adi, 2026-10-22: "too disjointed, FOCO just stands there, there's no story").** Cut five strangers at 1.5 s each plus a mascot card and an app screen, and it read as unrelated pieces. Follow one protagonist through stuck → uses FOCO → starts, and bring the mascot in through her phone/the app, never as a standalone card. Show a 4-5 frame storyboard before building.

## WordPress content encoding

- **WP rewrites a bare `&` in post content to `&#038;`, which turns `a&&b` into a JS syntax error.** Shipped a timer whose script died with "Invalid or unexpected token"; the widget rendered perfectly and did nothing. `<` and `>` pass through untouched, only `&` is hit. **Never use `&&` (or any bare `&`) inside an inline `<script>` pushed via REST** - use early returns or try/catch. `timer-widget.js` now throws at build time if the generated style/script contains one. Corollary: a 200 from the REST PATCH proves nothing; load the rendered page and check for `pageerror`.

- **Push CSS with `node scripts/inject-light.mjs [slug] --live`** (idempotent, dry-run by default; `--drafts` covers unpublished posts so publishing one does not re-ship an old block). The CSS lives inside each post's content between `<!--foco-light-start/end-->` because Customizer `custom_css` is not REST-writable. Editing `light-articles.css` alone changes nothing live.
- **Post bodies carry dark-theme colours as INLINE styles, which no class-based rule can reach.** 70 posts hand-write `color:#B8B0CC` (--muted) into example cards: correct on the dark card it was written for, 1.97:1 on the light page. Handled by darkening `[style*="color:#B8B0CC"]` article-wide and restoring it inside the dark islands. Verified first that **no post uses inline `background-color:`/`border-color:`**, so the substring can only hit a `color:` declaration. Same trick for `#0a0410`/`#7C3AED` inline backgrounds. Other inline colours (`#fff`, `#A78BFA`, `#FB923C`) sit on dark surfaces and already pass, so do NOT blanket-flip them.
- **Fix the whole class, then let the audit find the stragglers.** The site-wide sweep took 3 rounds: 50 failures on 11 pages, then 16 on 2, then 0. Each round the audit surfaced a pattern invisible from the first post (`.foco-cmp th` on a purple gradient in 73 posts, `blockquote` inheriting theme grey, `-num` badges white on orange). Never declare a CSS class of bug fixed from one page.

## Verification harness traps (2026-07-25)

- **`audit-contrast.js` injects its probe by replacing `</body>`, so a bare content fragment silently fails open**: it prints `probe did not run` and then `0 contrast failure(s)`, which reads exactly like a pass. Stage the real thing instead: `curl` a live post page, swap the inner HTML of its `<article>` for the draft's content, absolutize root-relative asset URLs, then audit that file. Doing this on the Wall of Awful post surfaced 4 real failures (white numerals on `#F97316`/`#D96A6A`/`#3F9D62` badges, 2.8:1 to 3.38:1) that the fragment run had reported as clean. Safe badge colours for white text: `#6D28D9`, `#B02A2A`, `#C2410C`, `#2E7A4B`.
- **Headless Chrome will not lay out narrower than ~500px**, so `--window-size=390` clips the screenshot instead of reflowing and fakes a mobile overflow bug. To test narrow layout, render the component inside a fixed-width container (300px / 340px) and assert `scrollWidth <= clientWidth` per element, plus no child's `right` past the container's.
- **`<!--foco-light-start-->` is stripped from the rendered page**, so grepping the live HTML for it always returns 0 even when the CSS shipped. Check for `FAF8FD` instead.
- **`node scripts/gap-scan.js "<concept>" [--query "<target query>"] [--drafts]`** is the pre-write cannibalization check: full-body-text concept scan plus a heading-collision check. A live post whose H3 already asks your exact target question is the real risk (that was the #1080 vs #1042 bug); the fix is trimming that heading to one sentence with a link out, not dropping the new post.

## Chart placeholders (silent no-op)

- **`<!-- FOCO_CHART:kind {json} -->` comments in post content are NOT rendered by anything live.** Post #2179 shipped with two of them (`statGrid`, `horizontalBar`) sitting invisibly in the body, which is why the post read as image-free while `chart-configs.js` looked "done". **When a post looks bare, grep its raw content for `FOCO_CHART` before assuming no visuals were ever planned.** Render them as light-native div figures (see `foco-statfig` / `foco-stagefig` in #2179) and delete the comment.
- **Check a placeholder's payload before rendering it.** The `horizontalBar` block carried invented unitless values (25/20/15/85) with no source. Do not promote fabricated numbers into a real chart just because a generator wrote them down - re-encode the claim qualitatively (stages, cards) or drop it.
- **The ASO assets in `../v2_1260x2736/` are the only real app screenshots on disk.** Crop the device out with sharp (`extract` then `resize({width:640})` -> webp ~60KB) rather than embedding the full marketing panel. Verify each crop by reading the PNG back.
- **`figure`/`figcaption` captions must not say "Left:"/"Right:"** - a flex-wrap two-up stacks vertically on mobile and the caption becomes wrong.

## create-post.js pitfalls

- **STEP 3 silently discards local file edits on an existing post.** It swaps your local `content` for live WP content whenever `wpContent.length > localFile.length * 0.8` — and once schema/CSS/TOC are injected, WP content is ALWAYS bigger than a raw source file, so this fires on nearly every re-run against an already-published post. Editing `posts-new/X.html` and re-running the pipeline can silently push the OLD content back while reporting success. **To edit a published post: GET the live content first, edit that fetched copy directly, then push via a direct REST POST** (or make the local file a full copy of current WP content before running the pipeline). Bit us on `amazing-marvin-alternative` (2026-09-18).
- **A comparison/alternative post with zero in-body images reads as thin and boring, even if the copy is fine.** The pipeline only warns ("NO in-body visuals"), it does not block. Real product screenshots (App Store `screenshotUrls` via `itunes.apple.com/lookup?id=...`, or a competitor's own marketing site) are fast to fetch and make the post feel built, not templated. Don't ship a competitor-comparison post without at least one real screenshot of the thing being compared.
- **STEP 9 unconditionally strips EVERY `<figure class="foco-img">` on every run**, logged misleadingly as "Stripped N legacy Pexels image(s)" — it does not check the image src, so it deletes real product screenshots exactly the same as old stock photos. Running `create-post.js` on a source file that already has real screenshots in it will silently delete them before the run finishes. **Add real screenshots AFTER running the pipeline** (fetch live content, patch the `<figure>` blocks in directly, push via REST), never in the source file you feed to `create-post.js`.
- **The locked P6 naming convention in CLAUDE.md is `foco-vs-X` (head-to-head), but most existing `posts-new/*-alternative.html` files use a roundup-with-FOCO-as-one-pick shape instead.** Check which convention the user actually wants before naming/structuring a new competitor post — don't just copy whichever existing file happens to be closest at hand.
- **Short-form video (2026-10-02):** each text block needs ~1.5s reading time per line and must stay on screen until the scene ends. Lead each item with the viewer's problem as a question, show the benefit visually (e.g. task-breakdown demo), 56px+ body text. First 4s/scene cut was "too fast, unclear, boring".
- **FOCO has a built-in calendar (2026-10-02).** I scripted "It's not a calendar, pair it with one" by copying the old review/article copy. Product claims about FOCO come from Adi or the live app, never from existing posts or video transcripts, which drift.
- **Carousels must show FOCO's whole process, not just the reveal (2026-10-05).** I kept FOCO to the last slide and skipped capture (voice/photo/text) and the calendar because the skill said so; Adi wants the full flow shown: capture, calendar, breakdown, focus with timer + music. Use the `phone` layout for real screenshots mid-carousel.
- **FOCO breakdown is a choice, not automatic (2026-10-05).** After a task lands in the calendar, the user picks whether to break it into steps with one AI tap. I wrote "it lands in my calendar, already broken into tiny steps"; correct copy is "one tap and AI breaks it into steps".
- **One task end to end in a process carousel (2026-10-05).** I mixed real screenshots of different tasks (Email my boss 25 min, Write mail 20 min, an 8-min subject-line step) and Adi called out the inconsistency. Same task name, total and steps on every slide; draw the screen when no matching screenshot exists.
- **Hooks must call out the audience and land the point in one second (2026-10-05).** "I needed to update one page. So I redesigned everything" read as a story, not a hook; Adi didn't get the point fast. Fix: "Freelancer with ADHD:" / "Task: update one page." / "Me: redesigns everything 🙃".
- **App demo videos = one continuous user flow, not a feature montage (2026-10-07).** I cut 7 unrelated screenshots (different tasks, different moments) into a "features" reel; Adi wanted to watch one task being created, split with AI, then focused on one step with music picked. The carousel lessons above apply to video too. For a demo, work from a screen recording of the real flow, not stitched stills.
- **Never render over an existing video (2026-10-07).** Adi said "don't overwrite, make a new one" for one version; I later re-rendered all six demos into the same filenames and lost the previous cuts. Every re-render goes to a new name (`-v2`, `-animated`), and the copy into `Downloads\final videos for foco` never replaces a file without asking.
- **FOCO is said "Foco" (like "focus"), never spelled F-O-C-O (2026-10-07).** ElevenLabs (Reelkit voices) read the all-caps word as an acronym. In any narration text sent to a TTS write "Foco"; keep "FOCO" only in on-screen text. Kokoro reads both the same.
- **TikTok/Reels safe zone for every vertical video (2026-10-07).** Text, captions, logos and badges placed at the very top or bottom got covered by the app UI after upload. Keep all important content between 14% and 75% of the height, and out of the right ~12% (like/share rail). Burned-in captions go at ~25% from the bottom, not 6-10%.
- Carousels: when a format starts to feel repetitive, invent a new format (e.g. the `chat` "Texting my ADHD brain" format, approved 2026-10-07) instead of rewording the old one. Keep: sharp narrator photo with face visible + a funny "villain" voice (her brain) + FOCO as one card at the turn.
- Carousels: rotate narrators (men + women, different ages, faceless POV), never the same girl in every carousel. Keep the message simple: 5 slides, 2 short messages each, one-step ending.
- **Check a build script's target before pushing (2026-10-09).** homepage-preview/build-page.js looked pages up by slug `home-preview`, which had become the LIVE homepage (4760); `--push` would have renamed it and set noindex. Now: default target is /home-draft/, `--live` writes page_on_front with a backup. Before any push script, confirm which page/post id it resolves to.
- **Theme class names collide (2026-10-09).** The theme already styles `.store-badge`, `.logo img`, `.blog-single article a` (underline). Prefix new classes (`fh-`, `fa-`) and inspect computed styles in Playwright when something renders with an unexplained frame/size.
- **Cloudways bot protection answers rapid checks with "One moment, please..."
